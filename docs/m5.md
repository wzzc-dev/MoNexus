# M5 — Task/Run scheduling, evidence gate, events and search

M5 turns the single ACP session into a small task system. A `Task` owns one or
more `Run`s; the host queues runs per machine, executes them in a Worktree,
runs the project's `verify[]` gate, and only then settles the task. Events are
the transport for every state change, and `search.sessions` indexes session
and decision text.

The milestone deliberately stops before M6 recovery and M7 packaging: there is
no crash-resume matrix for in-flight runs (after a host restart the projection
is rebuilt but no worker resumes them; `lost` is reserved for M6), no remote
agent execution, and no OS-level packaging.

## Data model

`packages/contracts/task.mbt` defines the state machines and records:

- **Task**: `draft → planned → ready → running → succeeded | failed |
  cancelled`, with `waiting_approval`/`waiting_owner`/`blocked` as owner- or
  evidence-driven branches. `parent_id` links subtasks; a parent does not
  automatically wait for its children — rollup is per task from its own runs.
- **Run**: `queued → running → verifying → succeeded | failed | cancelled`,
  plus `waiting_approval` (evidence failure), `waiting_input` and `lost`
  (host restart). `lost` is intentionally not terminal: M6 decides between
  retry and failure.
- Every Run binds `task_id`, `machine_id` (`""` = local), `workspace_id`,
  `worktree_id`, `mode` (`command|agent`), command/prompt and an
  `idempotency_key` (unique partial index in SQLite).

`packages/machines/task_store.mbt` owns the projections (`projects`, `tasks`,
`runs`, `evidence`, `search_docs`, optional `search_fts`) and writes the
append-only event and its projection in one transaction. Every host start
reconciles missing projections from the event log
(`store.reconcile_task_projection()`), which the replay test exercises by
appending events *without* projections and rebuilding.

## Scheduling

`run.create` validates the task (must be `ready` or later and not terminal),
the workspace, mode/command, optional worktree (must belong to the
workspace), and placement. Placement is:

- explicit `machine_id` — the machine must exist and be available; optional
  `requires {arch, os, tool}` must match;
- otherwise, capability match over local + registered machines (`uname` /
  `command -v` probe for `git gcc clang cmake moon node bun python3`);
- explicit machine still wins when `requires` is absent.

Capacity is per machine: local uses `MONEXUS_MAX_PARALLEL` (default 4), SSH
machines use `profile.max_parallel` (default 4). `dispatch_queued` holds a
`dispatching` guard, scans queued runs FIFO, and only starts them if the
machine has a free slot. `queued` does **not** occupy a slot; `running`,
`verifying`, `waiting_approval` and `waiting_input` do. A new dispatch also
wakes the queue, so cancelling the head frees capacity for the next run.

Dispatch is idempotent: `run.create` first looks up a non-empty
`idempotency_key`, and returns the existing Run instead of creating a second
one. The desktop currently sends fresh ids; scripts use stable keys to prove
the behavior.

## Execution and worktrees

`execute_started_run` resolves the worktree: an explicit `worktree_id` is
used as-is; otherwise the host creates `<root>-monexus-<short>` on branch
`monexus/<short>` (a `worktree.*` event is recorded) and runs there.

- `command` runs execute through the workspace provider (`/bin/sh -c` locally,
  `ssh target sh -c` remotely) with a timeout. Output is capped at 64 KiB and
  stored as a `run-output.log` artifact.
- `agent` runs are **local-only** in M5. They reuse M4's `handle_agent_start`
  with an internal Sink, poll `agent.read` until the session ends, and then
  enter the same verification step. A failed agent session fails the run.

Progress and heartbeats are events (`run.progress`, `run.heartbeat`); the Run
projection carries `output_summary`, `last_error` and `stop_reason`.

## Evidence gate

On a successful main step the run moves to `verifying`. For each command in
the task's `verify[]` (inherited from the project when the task has none) the
host:

1. executes it in the same worktree;
2. records an `EvidenceRecord` (`exit_code`, `passed`, `timed_out`, excerpt,
   artifact id);
3. writes `<state_dir>/runs/<run_id>/<name>.log` as a `text/plain` artifact
   (`artifact.created`);
4. emits `run.evidence`.

If every command passes (or the task has no `verify[]`), the run is
`succeeded` and the task rolls up. If any command fails, the run moves to
`waiting_approval` and a `Decision` of kind `verify` is created with options
`waive`, `retry` and `fail`, plus `run_id` and the evidence detail. There is
no silent success path.

`decision.respond` on a verify decision calls `handle_verify_decision_respond`:

- `waive` marks the failed evidence `waived`, then settles `succeeded`;
- `retry` re-enters `verifying` and re-runs the full gate;
- `fail` settles the run (and task) as failed.

Task rollup preference: any run `waiting_approval`/`waiting_input` →
`waiting_approval`; any `running`/`verifying`/`queued` → `running`; any failed
→ `failed`; all succeeded → `succeeded`; all cancelled → `cancelled`.
Cancelling a task cancels every non-terminal run and expires its pending
verify decisions.

## Events, cursor and search

All M5 state changes are `EventEnvelope`s in SQLite. `events.list` takes
`since` (exclusive) and `limit` (1–2000) and returns
`{events, next_seq}`. The desktop keeps its own cursor: the host-link worker
enqueues a task refresh on reconnect, and every `task.*`, `run.*`,
`artifact.*`, `decision.*` or `project.*` event wakes the worker; a refresh
lists tasks plus `events.list(since=cursor-1)`, and the model dedupes by
`seq` and caps the Activity tail at 200 entries. This is the “projection +
cursor subscription” path in the desktop; `events.subscribe` remains the live
transport.

`search.sessions` queries `search_docs` (written for every finished session
transcript and every Decision title/detail/answer). FTS5 is created
opportunistically; when the SQLite build or schema cannot use it, the same
query falls back to `LIKE` with a snippet. The RPC returns
`{hits:[{kind, ref_id, title, snippet, ts}], backend}` so the UI can show
which backend served the result.

## RPC surface

New methods: `project.create/list`, `task.create/list/get/cancel`,
`run.create/list/get/cancel`, `artifact.read`, `events.list`,
`search.sessions`.

`run.get` returns `{run, evidence, artifacts, diff}`; the diff is
`git --no-pager diff --no-color HEAD` in the run's worktree (empty when the
run has no worktree or the path is not a git repository). `artifact.read`
only serves files under the host state dir and caps the response at 256 KiB.

Desktop pages:

- **Tasks**: create a `ready` task (workspace defaults to the open Project),
  select a task, dispatch a command run to local or a machine id, cancel a
  task/run, and open a Run detail with status, evidence, artifacts and diff.
- **Activity**: the tail of the host event stream, refreshed through the
  cursor path above.
- **Search**: `search.sessions` hits with kind/ref/snippet and the backend.
- The task board and the open run detail also refresh after verify decisions,
  so a waiver/retry/fail from the Inbox is visible without a manual reload.

## Verification

`scripts/task_smoke.sh` (80 checks) covers:

1. project/task/run happy path on local: inherited verify, subtask
   `parent_id`, idempotent dispatch, evidence + artifacts + diff, artifact
   read, task rollup;
2. local `max_parallel=1`: second run queues, drains after the first finishes,
   cancellation, event types, stable cursor;
3. evidence gate: failed verify → `waiting_approval` + `verify` Decision;
   `waive` → succeeded with waived evidence; `retry` re-runs and asks again;
   `fail` settles failed; cancelling a task expires its pending decision;
4. search: decision text found, backend reported, no-match/empty query;
5. ephemeral loopback sshd: machine add/probe, SSH workspace, local + SSH runs
   on one task running concurrently, both succeeded, `2/2 runs succeeded`;
6. host restart: projections, run/evidence/artifacts/search survive and the
   event cursor is non-zero;
7. illegal transitions: terminal task/run, empty title/command, missing run.

`moon test --target native` adds pure state-machine/JSON tests in
`packages/contracts/task_test.mbt`, projection/idempotency/slot/search/replay
tests in `packages/machines/task_store_test.mbt`, and desktop state tests for
task creation, dispatch, event dedupe and search.

## Known limitations / leftovers

- No M6 recovery: in-flight runs are not resumed (or marked `lost`) after a
  host restart; startup only reconciles projections and the events survive.
- Agent runs are local-only; the agent step uses a dummy sink, so it does not
  stream to the Agents page. Use the Agents page for interactive ACP work.
- The evidence gate is serial per run and has no per-command timeout beyond
  the verify timeout (300 s); no parallel verify commands.
- `waive` currently applies to every failed evidence row of the run, not a
  selected row, and there is no waiver text/audit beyond the Decision answer.
- Search indexes finished sessions and decisions only; live transcripts are
  not indexed until finalize. FTS5 availability depends on the bundled SQLite,
  so this environment reports `backend: like`.
- Desktop task creation requires an open Project or a pasted workspace id;
  there is no project picker yet. Run dispatch supports command mode only
  from the UI (agent runs are available through RPC).
- The Tasks board refreshes whole lists on each relevant event (no delta
  protocol); the Activity tail is capped at 200 and only the latest 30 are
  rendered.
- `run.get` diff is capped/read at the host; large worktrees may still make
  the RPC slow.
- M7 packaging, installers and signed builds are out of scope.
