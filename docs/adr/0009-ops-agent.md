# ADR-0009：机管 Agent（`ops`）作为 V0.1 种子角色

- 状态：Accepted
- 日期：2026-11-25
- 依据：`docs/architecture.md` r5 §9.1、§11；owner 决策 D7（D1–D6 之后确认）

## 背景

多机器工作台需要日常的机器与 Workspace 运维：加机器、探测连通性、建/归档 Workspace、诊断失败的 Run。把这些动作只放在 UI 里会让多步操作难以复用和审计；交给一个不受约束的“运维通道”又违反单一权威与审批模型。owner 提出“是不是应该有个 Bot 去管理工作区/远程机器”，并采纳为 V0.1 种子角色。

## 决策

1. **角色而非特权**：`ops` 是组织内普通 Agent（`role=ops`），通过 host 对所有 Agent 开放的同一套 RPC/工具操作机器与 Workspace；不拥有绕过权威层的通道。
2. **V0.1 工具面**：`machine.list`/`machine.describe`、SSH 连通性检查、Workspace 创建/归档、Run 诊断（心跳、日志、退出码）；写操作（装工具链、删 Workspace、重启机器）一律进入 `waiting_approval` 并落 Decision。
3. **不进关键路径**：没有 `ops` 时 UI 仍能完成同样操作；`ops` 的价值是把多步操作收敛为一次可审计的 Run，并验证 Agent→工具→策略→审批链路。
4. **同一策略与审计**：`ops` 的命令受 §11 风险分级约束；每次策略判定、审批回答与写操作写审计事件，密钥不入事件/日志。
5. **演进**：V0.2 起扩展到例行巡检（磁盘/负载/失联机器）、失败任务重试与扩容建议；V0.1 不自动化这些。

## 后果

- V0.1 需要一个最小 `ops` 角色定义与工具白名单，但不需要独立调度器或常驻服务。
- 若策略/审批链路未就绪，`ops` 只能做只读诊断；写操作保持 UI 人工完成，不降低安全性。
- 后续若把巡检做成自动任务，仍需遵守同一审批与证据门，不新增旁路。
