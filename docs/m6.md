# M6 — recovery & safety

M6 makes the M5 Task/Run system survivable: a host restart, a desktop exit,
an SSH drop or a remote machine that goes silent must not turn into a silently
retried side effect. The rule from architecture §13 is **silence is not
exit**: a Run is settled only from an observed exit code or a verified result.
What cannot be observed becomes `unverifiable` and raises a Decision for the
owner.

## Durable execution

Command-mode Runs execute through tmux (`packages/providers/workspace`):

- session `monexus-run-<run id suffix>`;
- local logs `<state_dir>/runs/<run_id>/run.{log,exit}`;
- SSH logs `$HOME/.monexus/logs/<session>.{log,exit}` on the target (the start
  script reports `$HOME` so the host stores real absolute paths);
- the session wrapper writes the exit code to the marker file only after the
  command ends.

`durable_start` / `durable_poll` / `durable_stop` are provider APIs, so local
and SSH runs share one monitor. When tmux is absent the host degrades to the
M5 synchronous path (`durable=direct`); such a Run becomes `unverifiable` if
the host restarts mid-flight.

## Stop reasons and the recovery policy

`RunRecord.stop_reason` now includes:

| stop_reason | observed? | host action |
| --- | --- | --- |
| `exited` | exit code != 0 | retry once (attempt 2), then a `recovery` Decision |
| `lost` | session gone, no marker | retry once (attempt 2), then a `recovery` Decision |
| `unverifiable` | transport cannot observe | **never** auto-retried; `recovery` Decision immediately |
| `timeout` | host-side deadline | `recovery` Decision (no automatic loop) |
| `approval_denied` | owner | failed, audited |
| `verified` | gate passed / waived | succeeded |

A retry is a **new Run row** with `retried_from=<old id>`, `attempt+1` and a
deterministic `idempotency_key` (`<base>/retry/<attempt>`). Reconcile and
duplicate Decision answers therefore return the existing attempt instead of
creating a second one.

`services/host/recovery.mbt` implements:

- `reconcile_runs` — startup scan of every active Run. `running`: poll the
  durable session, reattach and resume the monitor; no session and no exit
  marker → `lost`; transport unavailable or no durable handle → `unverifiable`
  Decision. `verifying`: the gate may have been half-written, so it is marked
  `unverifiable` rather than re-run. `waiting_approval`/`waiting_input` keep
  their Decision across a restart (the Decision is host state, not an ACP
  pipe) and the Decision is re-created if the crash happened between the Run
  transition and the insert.
- `monitor_durable_run` — adaptive poll; polling errors are tolerated for
  `MONEXUS_RECOVERY_UNVERIFIABLE_MS` (default 15 s) so a short SSH drop does
  not fail the Run. Past that window the Run becomes `unverifiable`.
- `create_retry_run`, `apply_stop_policy`, `request_recovery_decision`,
  `handle_approval_decision_respond`, `handle_recovery_decision_respond`.

## One Decision queue, three Inbox sections

Approvals, Agent permissions/readiness, evidence-gate waivers and recovery
retries all use the same `DecisionRecord` and `decision.list/respond` path
(the M4/M5 queue). M6 adds:

- `kind=approval` — policy `ask` for a high-risk command. The Run is created
  in `waiting_approval`; approve returns it to the queue, deny fails it.
- `kind=recovery` — options `retry` / `fail` for lost, unverifiable, timeout
  and retry-exhausted Runs.

The host computes the Inbox bucket centrally with
`contracts.decision_inbox_bucket` and enriches `decision.list` with `inbox`
and `run_status`:

- `needs_you` — status `pending`;
- `waiting` — answered `retry`/`approve`/`allow_*` while the owning Run (or
  its retry attempt) is still active;
- `handled` — terminal answers, expiries and finished Runs.

The desktop Inbox renders those three sections and keeps only pending
Decisions actionable.

## Audit and secrets

`audit.recorded` events (listed with `audit.list`) carry `id`, `action`,
`actor`, `subject`, `target`, `policy`, `risk`, `outcome`, `detail`,
`decision_id`, `run_id` and `ts`. M6 writes audit records for:

- every policy verdict (`policy.verdict`, `policy.deny`, `policy.approval`,
  `policy.approve`, `policy.deny`);
- every Decision answer (`decision.respond`) and expiry (`decision.expire`);
- recovery actions (`recovery.escalate`, `recovery.reconnect`,
  `run.stop`, `run.retry`).

Secret handling follows ADR-0006 §5: `agent_env` values whose names look like
credentials are replaced with `[redacted]` before the Run is persisted; Run
summaries/errors, Decision detail, run/verify artifacts and all audit detail
pass `redact_secrets` (key/value, `Bearer`, `sk-` tokens and private-key
blocks). The owner-declared command text is kept verbatim because it is the
program to execute and the retry source — credentials must come from the
machine's logged-in Agent account, not from a command argument.

## Verification

`scripts/recovery_smoke.sh` (60 checks) uses a temp state dir, an isolated
`TMUX_TMPDIR`, and a fake `ssh` on `PATH` that executes commands locally and
can be switched to `disconnect` through a mode file. It covers:

1. desktop exit — the durable run keeps running and succeeds;
2. host `SIGKILL` mid-run — restart reconciles, reattaches tmux and the Run
   succeeds; `run.reconcile.reconnect` + `recovery.reconnect` audit exist;
3. host crash with the session deleted — `lost`, exactly one automatic retry,
   the retry succeeds;
4. short SSH disconnect — polling errors are tolerated, no Decision;
5. remote machine silent past the window — `unverifiable`, no auto retry,
   `recovery` Decision in `needs_you`; owner retry creates exactly one
   attempt; a duplicate answer is rejected; the Decision becomes `handled`
   after the retry succeeds;
6. `exit 7` — one retry, then a `recovery` Decision; total attempts stay 2;
7. policy deny / approval / approve, duplicate dispatch by
   `idempotency_key`, audit field completeness, secret-free artifacts and
   audit records.

Pure unit tests cover the policy classifier, redaction, audit round-trip and
Inbox bucket rules (`packages/contracts/policy_test.mbt`), plus the desktop
Inbox state flow (`apps/desktop/app/app_test.mbt`).

## Limits / leftovers

- `verifying` at restart is conservatively `unverifiable` (the gate is not
  re-entered); `run_verification` is not idempotent for provider side effects.
- A recovered Run without `worktree_id` falls back to the workspace root for
  verification; a host-managed worktree created but not yet attached when the
  host died can therefore verify in the wrong directory (the command itself
  already ran in the right cwd).
- `timeout` does not auto-retry; it always raises a Decision.
- Agent-mode Runs are not tmux-durable; their failure path keeps
  `execution_failed` (local-only M5 boundary).
- Direct (non-tmux) execution is `unverifiable` on a host restart, by design.
- `audit.list` scans the event log (bounded slice), not a dedicated index.
