## 1. MoonBit native 可执行

### 做了什么

- 仓库根新增最小 workspace：`moon.work`，成员 `./spikes/m0`。
- `spikes/m0/moon.mod` 声明 module `monexus/m0`、`preferred_target = "native"`，
  依赖 `moonbitlang/async@0.22.5`、`moonbit-community/pty@0.4.4`。
- `services/host` 用 `pkgtype(kind: "executable")`，`async fn main` 分派
  `version` / `help` / `pty-check` / `ssh-probe` / `ssh-run` / `acp`。

### 证据

```sh
$ export PATH="$HOME/.moon/bin:$PATH"
$ moon build --target native
Finished. moon: ran 3 tasks, now up to date
Artifacts:
  monexus/m0/services/host  native  .../_build/native/debug/build/services/host/host.exe

$ ./_build/native/debug/build/services/host/host.exe version
monexus-host 0.0.1-m0 (M0 spike)
# exit 0
```

- 连续两次 `moon build --target native` 均成功；第二次 `no work to do`。
- `moon test --target native`：3 个 SSH argv/quoting 单元测试全部通过。
- 产物是原生可执行文件，真实打印版本并以 0 退出；不是仅编译通过。

**结论：PASS。** `moon.work` 与 spike 代码一并提交，构建可重复。

## 2. 本地 PTY

### 做了什么

`services/pty_spike`（M1 已迁移到 `packages/providers/pty`）直接复用 `moonbit-community/pty@0.4.4`（Apache-2.0），也就是
MoSpace `services/terminal` 使用的同一个 PTY 包；没有拷贝 MoUI
`examples/terminal/pty_host` 的 C 源。启动 `sh`，写入一整行命令（自动补换行），
`read_all()` 读到 EOF 后 `wait()` 拿退出码。

### 证据

```sh
$ host.exe pty-check --shell sh --cmd "printf 'M0_PTY_OK\n'; exit 7"
M0_PTY_SHELL=sh
M0_PTY_PID=1377714
M0_PTY_EXIT=7
M0_PTY_OUTPUT_BEGIN
printf 'M0_PTY_OK\n'; exit 7
$ M0_PTY_OK

M0_PTY_OUTPUT_END
# exit 0
```

- 看到 shell 回显与命令输出 `M0_PTY_OK`。
- 子进程真实 PID（每次不同）与退出码 7 均由 PTY 侧取得。
- 平台：Linux x86_64。

**结论：PASS（Linux x86_64）。**

## 3. SSH 执行

### 做了什么

- `SshTarget` + `ssh_argv` + `shell_quote` 按 MoSpace `services/remote`
  （Apache-2.0）的结构重写：`BatchMode=yes`、`ConnectTimeout=`、单引号转义。
- 远程 argv 不拼成 shell 字符串。实际命令固定为：

  ```sh
  sh -c 'cd -- "$1" && shift && exec "$@"' monexus-run <quoted cwd> <quoted argv...>
  ```

  argv 元素是位置参数，`;`、`$()`、单引号等保持数据。
- `probe` 执行只读固定脚本：`uname -s/-m/-r`、`$SHELL`、`command -v`
  git/gcc/clang/cmake/moon。
- 测试用临时非 root sshd（127.0.0.1 随机端口）：临时 host/client key、临时
  `AuthorizedKeysFile`、`UsePAM no`、`StrictModes no`；客户端用
  `StrictHostKeyChecking=accept-new` + 临时 `UserKnownHostsFile`。未改
  `~/.ssh/config` 与用户全局 `known_hosts`。

### 证据：probe

```text
M0_SSH_PROBE_OK
os=Linux
arch=x86_64
kernel=6.8.0-147-generic
shell=/usr/bin/zsh
tool.git=/usr/bin/git
tool.gcc=/usr/bin/gcc
tool.clang=<missing>
tool.cmake=/usr/bin/cmake
tool.moon=<missing>
# exit 0
```

`moon` 显示 `<missing>` 是如实结果：远程非登录 shell 的 `PATH` 不含
`~/.moon/bin`。这反而说明 probe 没有被硬编码糊弄。

### 证据：远程命令与退出码

```sh
host ssh-run ... --cwd /tmp -- sh -c 'printf "REMOTE_OK=%s\n" "$(hostname)"; exit 3'
```

```text
M0_SSH_RUN_EXIT=3
M0_SSH_STDOUT_BEGIN
REMOTE_OK=ubunutu2404

M0_SSH_STDOUT_END
M0_SSH_STDERR_BEGIN

M0_SSH_STDERR_END
# host 进程 exit 3
```

### 证据：argv 注入探针

```sh
host ssh-run ... --cwd /tmp -- printf '%s\n' \
  'a b; echo INJECTED' '$(echo SUBST)' "it's" '--not-a-flag'
```

```text
M0_SSH_RUN_EXIT=0
M0_SSH_STDOUT_BEGIN
a b; echo INJECTED
$(echo SUBST)
it's
--not-a-flag

M0_SSH_STDOUT_END
# exit 0
```

没有出现单独一行的 `INJECTED` 或 `SUBST`，说明 `;` 与 `$()` 没有被远端 shell
执行；带空格的参数也保持为单个 argv。

**结论：PASS（loopback 真实 sshd + 真实 ssh 客户端）。**
**未验证：** 外部机器、跨网络、主机密钥策略、密码/跳板机认证。

## 4. ACP stdio 会话

### 做了什么

`services/acp_client` 实现顺序 JSON-RPC 2.0 stdio 客户端：

`initialize` → `session/new` → `session/prompt`，期间处理 `session/update`
通知并打印 `agent_message_chunk`，直到 prompt 响应里的 `stopReason`。stderr
单独 drain 并加 `[acp stderr]` 前缀。协议形状参考 MoUI
`acp_native_transport`（Apache-2.0），未拷贝代码。

### 4a. mock agent（传输层 + 权限请求路径）

```sh
host acp --command node \
  --arg spikes/m0/tests/mock_acp_agent.mjs \
  --workspace "$PWD" --cwd "$PWD" --prompt 'say hi' --timeout 30
```

```text
M0_ACP_STREAM_BEGIN
M0_ACP_CHUNK MOCK:
M0_ACP_CHUNK  hello
M0_ACP_CHUNK  from
M0_ACP_CHUNK  ACP
M0_ACP_CHUNK  #1
M0_ACP_STREAM_END
M0_ACP_SESSION_ID=mock-session-1
M0_ACP_AGENT=mock-acp-agent
M0_ACP_CHUNKS=5
M0_ACP_UPDATES=5
M0_ACP_PERMISSION_REQUESTS=0
M0_ACP_TEXT=MOCK: hello from ACP #1
M0_ACP_DONE stop_reason=end_turn
# exit 0
```

权限路径：prompt 含 “permission” 时 mock 发
`session/request_permission`；客户端计数并回复 `{"outcome":{"outcome":
"cancelled"}}`，仍完成本轮：

```text
M0_ACP_PERMISSION_REQUESTS=1
M0_ACP_DONE stop_reason=end_turn
# exit 0
```

M0 没有 Decision/收件箱通道，因此故意拒绝而不是静默同意——这是安全上的正确
默认，也是 M4 必须补的接口。

### 4b. 真实 ACP agent（`@zed-industries/claude-code-acp@0.16.2`）

测试依赖安装（仅本地）：

```sh
npm install --prefix spikes/m0/.testdeps --no-audit --no-fund \
  @zed-industries/claude-code-acp@0.16.2
```

从 Claude Code 会话里启动必须 `env -u CLAUDECODE`，否则 adapter 拒绝嵌套会话：

```sh
env -u CLAUDECODE host acp \
  --command spikes/m0/.testdeps/node_modules/.bin/claude-code-acp \
  --workspace /tmp/m0-acp-ws --cwd /tmp/m0-acp-ws \
  --prompt 'Reply with exactly M0_ACP_REAL_OK and nothing else.' --timeout 170
```

```text
M0_ACP_STREAM_BEGIN
M0_ACP_CHUNK 
M0_ACP_CHUNK M
M0_ACP_CHUNK 0
M0_ACP_CHUNK _
M0_ACP_CHUNK ACP
M0_ACP_CHUNK _RE
M0_ACP_CHUNK AL
M0_ACP_CHUNK _OK
M0_ACP_STREAM_END
M0_ACP_SESSION_ID=5fd31988-a83c-4974-a647-b7c716768298
M0_ACP_AGENT=@zed-industries/claude-code-acp
M0_ACP_CHUNKS=8
M0_ACP_UPDATES=9
M0_ACP_PERMISSION_REQUESTS=0
M0_ACP_TEXT=M0_ACP_REAL_OK
M0_ACP_DONE stop_reason=end_turn

```

这是真实 agent 进程、真实 stdio JSON-RPC、真实模型流式返回；不是 mock。
使用的是调用方的 Claude 凭据与网络，因此该步骤在 `run_all.sh` 中默认跳过，
需 `M0_REAL_ACP=1` 显式开启。

### 4c. codex-acp（未验证）

`@zed-industries/codex-acp@0.16.0` 已装为本地测试依赖，但本机 Codex 未登录：

- 默认 `CODEX_HOME=~/.codex` 时，本机 `magpie-models.json` 的
  `reasoning effort: ultra` 不被内置 codex 接受，adapter 启动即失败；
- 清空 `CODEX_HOME` 重试后，协议走到认证：

```text
M0_ACP_AGENT=codex-acp
M0_ACP_ERROR ACP error response: {"code":-32000,"message":"Authentication required"}
```

因此 codex 路径记为 **UNVERIFIED（认证原因）**，不作为 MoNexus 传输失败。

**结论：ACP stdio 传输 PASS；真实 agent PASS（claude-code-acp）；权限请求
路径 PASS（mock）；codex UNVERIFIED（未登录）。**

## 阻塞项与风险

1. **ACP 权限没有 Decision 通道**：当前统一回 `cancelled`。M4 必须把
   `session/request_permission` 映射到架构 §6.3/§11.2 的 Decision/收件箱，
   否则 agent 无法获得用户批准。
2. **真实 ACP adapter 是 Node 进程**：`claude-code-acp` 包装 Claude Agent SDK；
   `codex-acp` 包装 Codex。它们只能作为受控 sidecar，不是产品关键路径依赖。
   其安装、版本、认证和生命周期都需要在 M4 明确。
3. **只有 loopback SSH**：跨机网络、NAT、跳板机、主机密钥轮换、密码认证未验证；
   `BatchMode=yes` 也意味着不能交互式输入密码。
4. **ACP 客户端是顺序的**：没有并发请求、cancel 队列、bounded buffer、
   `session/load` 恢复；真实 agent 的 tool call/权限/多轮场景未覆盖。
5. **PTY 只做最小闭环**：没有 resize、信号/终止、滚动缓冲背压、shell 集成；
   `read_all` 到 EOF 的模型适合 spike，不适合长期会话。
6. **远程工具探测受 PATH 影响**：非登录 shell 下 `moon` 缺失。M2 探测应明确
   是登录 shell 还是受控 PATH，且把结果按能力而非“工具存在”建模。
7. **测试环境依赖**：mock/真实 agent 需要 Node；端口选择用 Python；两者都只在
   `tests/` 与 `.testdeps/`，不进入产品。

## M1–M4 建议

### M1（桌面壳 + host 连接）

- 把 spike 的 `SshTarget`/`probe`/`run` 提升为正式的 Provider 契约；命令参数
  继续只接受 argv，禁止 shell 字符串入口。
- 定义 `ProviderError`：认证失败、连接超时、远端非零、host 超时分开建模；不要
  把 ssh 的 255 与远端命令退出码混为一谈（spike 已按此区分）。
- 保留 `ssh_target_test.mbt` 一类纯函数测试并纳入 CI；进程超时/取消要有统一
  backstop。
- host 仍是 MoonBit 可执行；Node/Python 不得出现在 host 或其启动路径。

### M2（机器注册 / SSH）

- 用真实外部机器做一轮矩阵：密码/密钥、跳板机、不同 `known_hosts` 策略、
  网络中断、远端退出码、超时取消。
- 认证探测（`probe`）与业务命令分离；明确登录 shell 与 PATH 策略，像
  `moon` 缺失这类结果要能展示给用户。
- 明确主机密钥策略（首次接受/固定指纹/手动确认）与 key 存储；继续保证测试
  不碰用户全局 SSH 配置。
- 评估 `ControlMaster`/连接复用与并发执行；当前每条命令一个 ssh 进程。

### M3（Workspace / 终端）

- PTY 继续用 `moonbit-community/pty`；补 resize、kill/信号、EOF 与退出码语义、
  有界 scrollback 与背压。
- 本地/远程终端统一抽象，为后续 tmux 重连留出接口；现在不实现 tmux。
- 写路径/argv 一律复用 `shell_quote` 或直接 argv，禁止把用户输入拼进 shell。

### M4（Agent 会话）

- **adapter 策略**：以 `claude-code-acp` 作为首个真实 ACP adapter，作为显式
  sidecar 管理（发现、版本、启动、stderr 归集、退出清理）；`codex-acp` 作为
  第二选项，需先解决认证/配置。不要把 Node 放进 host 关键路径。
- **readiness/auth**：开工前做能力探测（ACP 版本、认证状态、模型可用），缺失
  时给明确错误，而不是让 prompt 超时。
- **权限**：把 `session/request_permission` 转成 Decision/收件箱，携带
  toolCall、options、session 上下文；用户未决时不得默认 allow。
- **流式**：`session/update` 进有界队列，UI 慢时不阻塞 agent；区分 message /
  thought / tool call；支持 cancel 与 stop reason 透传。
- **恢复**：只有 agent 声明 `loadSession` 时才尝试 `session/load`；测试断线、
  重启、agent 已退出等场景。
- **测试**：保留 mock 作为无网络 CI 门槛；真实 adapter 作为手动/夜间可选门
  （`M0_REAL_ACP=1` 模式），记录认证与网络前提。`CLAUDECODE` 这类嵌套保护要在
  启动器里显式处理，而不是让它误报成协议错误。
